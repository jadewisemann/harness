# AI 작업 스키마(문서 정본 체계) 도입

이 저장소에 아래의 **에이전트 작업 스키마**를 도입한다. 다른 프로젝트에서 운영하며 검증한 체계이고, 핵심은 세 가지다:

1. **문서가 설계의 정본이다.** 코드는 How, 문서는 What / Why / Invariant를 말한다. 에이전트가 매번 코드에서 아키텍처를 역추론하지 않는다.
2. **모든 작업은 Understand → Implement → Reconcile 사이클을 거친다.** 구현 후 문서와의 일관성 검토가 의무다.
3. **커밋 게이트 훅이 그 검토를 강제한다.** 아키텍처 민감 영역이 문서 변경 없이 커밋되려 하면 딱 한 번 멈추고 검토를 요구한다.

파일 이름과 규칙 골격은 그대로 유지하고, **내용(설계 원칙·민감 경로·검증 명령)만 이 저장소에 맞게 채워라.**

---

## 0. 도입 절차 (네가 할 일)

1. 저장소 구조와 기술 스택을 파악하고 "작업 디렉터리" 단위를 정한다 — 단일 패키지면 루트 하나, 모노레포면 패키지(예: `backend/`·`frontend/`)별로.
2. §1의 문서 파일들을 생성한다. `DESIGN.md`는 **현재 코드에서 추출해** 초안을 만들되, 작성 기준 시점(날짜·기준 커밋)을 문서 머리에 명시한다 — 권위를 문서로 뒤집기 전에 코드 기준으로 한 번 동기화하는 것이며, 이 시점 이후의 어긋남만 "판정 대상"이 된다.
3. `docs/adr/0001-design-doc-authority.md`로 "설계 문서를 정본으로 승격한다"는 결정 자체를 ADR로 남긴다(§2의 권위 규칙, 기준선 동기화, 코드가 정본인 예외 목록 포함).
4. Claude Code를 쓴다면 §5의 커밋 게이트 훅을 설치한다 — 이 스킬 폴더의 `assets/design-review-gate.mjs`를 대상 저장소의 `.claude/hooks/design-review-gate.mjs`로 복사하고, 파일 안의 `SCOPES`(민감 경로·문서 경로)만 이 저장소에 맞게 수정한다.
5. 기존 `CLAUDE.md`에 내용이 있으면 `AGENTS.md`로 이관하고, `CLAUDE.md`는 포인터로만 남긴다.
6. 초안이 완성되면 사용자와 검토한다. 검토 전에는 push·PR을 임의로 만들지 않는다.

## 1. 파일 체계 — 누가 무엇의 정본인가

### 루트

| 파일 | 역할 |
|---|---|
| `CLAUDE.md` | **포인터 전용.** "AGENTS.md를 읽고 그대로 따른다" 한 줄만. 내용을 갖지 않는다 (Codex 등 다른 에이전트와 정본을 공유하기 위해) |
| `AGENTS.md` | **에이전트 작업 방식의 정본.** 저장소 정보, 절대 규칙, 브랜치·커밋·PR 컨벤션 요약, 작업 사이클. Git 상세의 SSOT는 `CONTRIBUTING.md`이고 여기는 에이전트용 요약 — 충돌 시 CONTRIBUTING.md 우선을 명시 |
| `CONTRIBUTING.md` | Git 협업 규칙의 단일 기준(사람·에이전트 공용) |

### 작업 디렉터리마다 (예: `backend/`, `frontend/`)

| 파일 | 역할 | 규약 |
|---|---|---|
| `CLAUDE.md` | 포인터 전용 | 같은 폴더 `AGENTS.md`로 안내, 공통 규칙은 루트로 안내 |
| `AGENTS.md` | **이 디렉터리에서 일하는 방식의 정본** | 구성: ① source-of-truth 표 ② 문서-코드 충돌 판정 규칙 ③ 작업 사이클(§3) ④ 검증 명령 ⑤ 테스트 최소화 원칙 ⑥ 코드 배치 규칙 |
| `DESIGN.md` | **설계·불변식의 정본** | "코드는 How, 이 문서는 What/Why/Invariant" 선언으로 시작. 번호 매긴 핵심 원칙(각각이 위반 판정 가능한 불변식), 아키텍처 다이어그램, 코드 구조와 경계 규칙, 하위 문서 지도(인덱스), **「코드가 정본인 것들」 예외 목록** |
| `docs/design/*.md` | 하위 시스템 상세 설계 | DESIGN.md의 지도에서 필요한 것만 연다. 각 페이지 상단에 SSOT 코드 경로를 달아 코드와 대조 검증 가능하게 한다 |
| `docs/adr/NNNN-*.md` | 결정의 이유 — "왜 이렇게 안 했는가" | 형식: 상태 / 날짜 / 맥락 / 결정 / 검토한 대안 / 결과 |
| `PLANS.md` | **진행 중** 변경의 계획서 | 목표·원칙·단계별 체크리스트·완료 기준. 끝난 계획은 지우고 결과를 DESIGN.md에 반영한다 |
| `IMPLEMENTATION_NOTES.md` | 휘발성 working memory | 작업 중 발견한 숨은 불변식·실측값·edge case·실패한 접근을 `## YYYY-MM-DD - 주제` 아래 불릿으로, 최신이 위. 영구 지식은 승격 후 여기서 지운다 |
| (선택) `docs/…/code-rationale.md` | 실측값·실패한 대안·함정 모음 | "값을 바꾸거나 단순화하기 전에 해당 심볼을 여기서 먼저 찾아본다". 코드 주석을 슬림하게 유지하는 대신 근거를 이곳에 집적 |

## 2. 권위 규칙 (문서 우선)

- 문서와 코드가 충돌하면 **조용히 코드를 따르지 않는다.** 구현이 틀렸는지, 설계 의도가 바뀐 것인지 **판정**한다 — 의도가 바뀐 것이면 DESIGN.md(또는 해당 하위 문서)를 고치고, 구현이 틀린 것이면 구현을 고친다. 판정 근거는 IMPLEMENTATION_NOTES.md에 남긴다.
- **예외: 기계가 소비하는 계약 파일은 계속 코드가 정본이다** (프로토콜 타입 정의, 디자인 토큰, 카탈로그·스키마 등). 이 예외 목록을 DESIGN.md에 명시하고, 문서는 이들을 서술만 한다.
- 문서는 사람과 에이전트가 함께 수정한다 — 사람은 의도가 바뀔 때, 에이전트는 Reconcile 단계에서 현실을 반영할 때. 둘 다 PR 리뷰를 거친다.

---

## 3. 작업 사이클: Understand → Implement → Reconcile

모든 작업(작은 티켓 하나 포함)이 이 3단계를 거친다. 각 디렉터리 AGENTS.md에 그대로 적는다.

### 1. Understand — 코드보다 모델 먼저

1. `DESIGN.md`에서 관련 원칙·불변식을 읽는다.
2. 지도가 가리키는 하위 시스템 문서에서 **해당 시스템만** 읽는다. 관련 없는 문서는 열지 않는다.
3. `IMPLEMENTATION_NOTES.md`(있으면 code-rationale.md)에서 관련 발견·함정을 확인한다.
4. 필요한 코드만 조사하고, **변경이 현재 설계에 어떻게 들어맞는지 설명할 수 있어야** 구현을 시작한다.

### 2. Implement — 모델 안에서 구현

5. 구현한다. **설계 위반이 필요해 보이면 구현을 멈추고** DESIGN.md/ADR 쪽 논의로 돌아간다.
6. 작업 범위에 필요한 만큼만 검증한다(§6).
7. 작업 중 발견한 숨은 불변식·실측값·edge case·실패한 접근은 즉시 날짜와 함께 `IMPLEMENTATION_NOTES.md`에 기록한다.

### 3. Reconcile — 모델을 현실에 맞춘다

8. `git diff`를 DESIGN.md·관련 하위 문서와 대조한다 — 새 숨은 가정이 생기지 않았는가? 문서가 서술하는 동작이 바뀌지 않았는가?
9. 정신 모델이 바뀌었으면 문서를 갱신한다. 구조적 결정이 새로 내려졌으면 ADR을 추가한다.
10. IMPLEMENTATION_NOTES.md의 영구 지식은 성격에 따라 **승격**한다 — 설계·불변식은 DESIGN.md, 동작 상세는 하위 시스템 문서, 함정·실측값은 code-rationale.md. 승격한 항목은 notes에서 지운다.
11. PLANS.md의 해당 단계 체크리스트를 갱신한다.

> **강제되는 것은 "문서 수정"이 아니라 "문서와의 일관성 검토"다.** 단순 버그 수정·스타일 변경에 의미 없는 문서 diff를 만들지 않는다.

## 4. Git 공통 규칙 (루트 AGENTS.md에 요약, 프로젝트에 맞게 조정)

- **main 직접 커밋/push 금지.** 항상 `feature/*`·`fix/*` 브랜치에서 작업하고 PR로 병합. Protected Branch가 꺼져 있으면 그 사실을 명시하고 규칙으로 지킨다.
- 공유 브랜치는 rebase·force push 금지. 히스토리 재작성은 사용자 승인 + 원격 백업 브랜치 후에만.
- 사용자가 명시적으로 요청하지 않는 한 **push·PR 생성은 먼저 확인**받는다.
- 브랜치: `<prefix>/<짧은-영문-설명>` — prefix는 대표 커밋 type(`feature/`·`fix/`·`refactor/`…), 소문자+하이픈+영문만, 브랜치 하나 = 작업 하나.
- 커밋: `<type>: <제목>` (feat/fix/docs/style/refactor/test/chore, 50자 내외, 끝 마침표 X).
- **병합은 언제나 Squash, 예외 없음.** PR 제목이 곧 squash 커밋 제목이므로 커밋 컨벤션과 같은 형식으로. CLI/API 병합 시에도 `merge_method: "squash"`. 병합 후 작업 브랜치 삭제.
- 과거 사고 사례가 있으면 규칙 옆에 그대로 남긴다("PR #9·#10·#11이 merge commit으로 들어가 히스토리를 재작성해야 했다" 같은 것) — 에이전트가 규칙의 무게를 알게 된다.

## 5. 커밋 게이트 훅 (Claude Code 사용 시)

대상 저장소의 `.claude/settings.json`에 등록:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": "node .claude/hooks/design-review-gate.mjs" }
        ]
      }
    ]
  }
}
```

훅 본체는 **이 스킬 폴더의 `assets/design-review-gate.mjs`를 그대로 복사**해 `.claude/hooks/design-review-gate.mjs`로 두고, 파일 안의 **`SCOPES`만 이 저장소에 맞게** 수정한다. 감시 범위를 정하는 철학: 설계 우선 개발 중인 영역은 `src` 전체를, 안정된 영역은 계약·규칙 표면(프로토콜·전역 store·도메인 로직)만 — 모든 변경마다 발동하면 소음이 되어 무시된다.

훅 동작(멈추는 조건, "같은 커밋 재실행이면 통과", 테스트만 바뀐 커밋은 제외)을 디렉터리 AGENTS.md에도 한 문단으로 서술한다.

## 6. 검증·테스트 최소화 원칙 (각 디렉터리 AGENTS.md에)

- 검증 명령 목록을 명시한다(예: lint+format / typecheck / 단위 테스트 / 빌드 / 순환 의존 검사 / E2E). **작업 범위에 필요한 검증만** 실행하고, 모든 명령을 관성적으로 돌리지 않는다.
- 테스트는 명확한 회귀 위험이나 완료 조건이 있을 때만 작성·실행한다. 정적 스타일·단순 마크업 변경은 typecheck+build까지만.
- 미래 요구를 예상한 테스트, 구현을 반복하는 테스트, 단순 렌더링 확인 테스트는 추가하지 않는다.
- 변경 범위와 직접 관련된 기존 테스트만 우선 실행하고, 전체 테스트는 통합·배포 단계에서.
- **검증 개수를 작업 품질로 간주하지 않는다. 작업 위험과 완료 조건에 비례해 검증한다.**

## 7. 이 체계가 잘 작동하게 하는 세부 습관 (문서 작성 시 반영)

- **불변식은 판정 가능하게 쓴다.** "물리는 연출이다 — physics result != game result. 클라이언트 물리 결과를 서버 상태에 반영하는 구현은 설계 위반이다"처럼, 위반 여부를 diff만 보고 판정할 수 있는 문장으로.
- **낡은 문서는 명시적으로 격하한다.** 명세로 쓰면 안 되는 문서가 있으면 "⚠️ 이 문서는 실제 계약보다 낡았다 — 명세로 쓰지 않는다"를 정본 문서에 적는다.
- **동작 차이(버그 포함)는 조용히 '개선'하지 않는다.** 기록 후 재현/수정 여부를 명시적으로 결정한다.
- 하위 시스템 문서·NOTES는 필요할 때만 여는 구조로 — 컨텍스트 절약이 이 스키마의 목적 중 하나다.
